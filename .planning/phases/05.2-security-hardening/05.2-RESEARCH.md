### Locked Decisions

**PBKDF2 Iteration Increase (sec-4)**
- Increase from 10,000 to 100,000 iterations in both `encryption-internals.ts` and `encryption-internals.web.ts`
- Migration strategy: re-encrypt on next file access (gradual, no downtime, no batch script)
- Store iteration count in encryption metadata alongside existing keyId, algorithm, iv, authTag fields
- Decrypt uses stored iteration count from metadata; encrypt always uses current default constant
- Files encrypted before this change have no iterations field in metadata, treat missing as 10,000 (backward compat)
- Re-encryption happens silently after successful decrypt, no user notification

**OpenID Redirect Restriction (sec-5)**
- Remove the unconditional `localhost` allowance in `isValidRedirectUrl()` (openid.js line 444)
- Allow localhost redirects only when `server_hostname` itself is a localhost URL (auto-detects dev vs production from existing config, no new env var)
- Validate hostname, port, AND scheme must all match server_hostname (prevents open redirect and HTTP downgrade)
- Error handling: return existing `{ error: 'invalid-return-url' }` code with a server-side `console.warn` logging the blocked URL

**Password Strength Requirements (sec-7)**
- Minimum 8 characters, no complexity rules (NIST 800-63B: length over complexity)
- Enforce on new passwords and password changes only, not retroactively on login
- Server-side validation in `isValidPassword()` (password.ts), no client-side JavaScript validation
- Return specific error codes (e.g. 'password-too-short') so frontend can show actionable feedback
- Existing passwords continue to work without forced change

**ReDoS Protection (sec-17)**
- Protection mechanism: execution timeout (~1 second) on regex operations, no external library
- Failed or timed-out regex operations: log warning, return original value unchanged (non-disruptive)
- Escape metacharacters in regex helper's non-regex mode (`new RegExp(value)` on line 53) to prevent accidental ReDoS from payee names
- Also escape metacharacters in replace helper's plain string mode for consistency

## Summary

This phase applies four targeted security hardening fixes to the Actual Budget sync-server and loot-core packages. The changes are surgical: each fix is self-contained to one file or one function with minimal caller impact.

The PBKDF2 change is the most complex because it requires backward-compatible metadata migration. The metadata object returned by `encrypt()` already carries `keyId`, `algorithm`, `iv`, and `authTag`. Adding an `iterations` field follows the same pattern. The critical constraint is that `decrypt()` must read iterations from metadata (defaulting to 10,000 for old files), while `encrypt()` and `createKey()`/`createKeyBuffer()` always use the new constant. Re-encryption is triggered after a successful decrypt+file-open cycle.

The OpenID redirect fix, password strength fix, and ReDoS protection are each a few lines of code. The main research value here is confirming exact function signatures, all call sites, and the frontend error message map pattern so no callers are left broken.

**Primary recommendation:** Make all four changes in a single plan wave ordered as: (1) encryption internals + metadata migration, (2) password validation + frontend error message, (3) OpenID redirect restriction, (4) ReDoS metacharacter escape + timeout guard. Test each with the existing vitest suite after every change.

### Pattern 1: Metadata Extension for PBKDF2 Migration

**What:** Add `iterations` field to the encryption metadata object. Decrypt reads it (with fallback). Encrypt writes current constant.
**When to use:** Any time a PBKDF2 parameter needs to be versioned without breaking existing files.
**Example:**
```typescript
// Source: packages/loot-core/src/server/encryption/encryption-internals.ts (existing pattern)

// NEW constant (replaces hardcoded 10000)
const PBKDF2_ITERATIONS = 100_000;
const PBKDF2_ITERATIONS_LEGACY = 10_000;  // for backward compat default

// createKeyBuffer: accept iterations param, default to PBKDF2_ITERATIONS
function createKeyBuffer({ numBytes, secret, salt, iterations = PBKDF2_ITERATIONS }) {
  return crypto.pbkdf2Sync(
    secret || crypto.randomBytes(128).toString('base64'),
    salt || crypto.randomBytes(32).toString('base64'),
    iterations,
    numBytes || 32,
    'sha512',
  );
}

// createKey: now returns iterations alongside the key material
export function createKey({ secret, salt }) {
  const iterations = PBKDF2_ITERATIONS;
  const buffer = createKeyBuffer({ secret, salt, iterations });
  return {
    raw: buffer,
    base64: buffer.toString('base64'),
    iterations,  // NEW: caller can store this in metadata
  };
}

// decrypt: reads iterations from meta, falls back to legacy value
export function decrypt(masterKey, encrypted, meta) {
  // ... existing setup ...
  // key was already derived with the iterations in meta.iterations when it was created
  // decrypt itself does not re-derive the key - the key is already loaded
  // meta.iterations is used when re-creating the key on file open
}
```

**Important architectural note:** The key derivation (PBKDF2) happens in `createKey()`/`createKeyBuffer()`, NOT in `decrypt()`. The `decrypt()` function receives an already-derived `masterKey`. So the migration cannot happen at `decrypt()` time. It must happen at the level where the key is created from password + salt. The `iterations` field must be stored in the file's key metadata (alongside `id`, `salt`, `base64` in async storage) so that when a file is re-opened, `createKey()` is called with the stored iterations. After successful file open, re-encryption uses a new key derived with 100K iterations.

See `packages/loot-core/src/server/encryption/app.ts` `keyTest()` for how `createKey()` is called with `id` + `password` + `salt` retrieved from the sync server. The `test.meta` object in that function is the `{ keyId, algorithm, iv, authTag }` tuple - this is what needs `iterations` added.

### Pattern 2: Server-Hostname-Based Redirect Validation

**What:** Replace the hardcoded `|| redirectUrl.hostname === 'localhost'` with a check against serverUrl itself.
**When to use:** Any multi-tenant or configurable-hostname server where dev/prod detection must come from config, not hardcoded strings.
**Example:**
```javascript
// Source: packages/sync-server/src/accounts/openid.js (current code to modify)

export function isValidRedirectUrl(url) {
  const serverHostname = getServerHostname();

  if (!serverHostname) {
    return false;
  }

  try {
    const redirectUrl = new URL(url);
    const serverUrl = new URL(serverHostname);

    // REMOVE: || redirectUrl.hostname === 'localhost'
    // REPLACE with: scheme + hostname + port must all match serverUrl
    const hostnamesMatch = redirectUrl.hostname === serverUrl.hostname;
    const portsMatch = redirectUrl.port === serverUrl.port;
    const schemesMatch = redirectUrl.protocol === serverUrl.protocol;

    if (hostnamesMatch && portsMatch && schemesMatch) {
      return true;
    } else {
      console.warn(`[openid] Blocked redirect URL: ${url} (server: ${serverHostname})`);
      return false;
    }
  } catch {
    return false;
  }
}
```

- `packages/sync-server/src/app-account.ts` line 88: checks `isValidRedirectUrl(req.body.returnUrl)` - no change needed
- `packages/sync-server/src/accounts/openid.js` line 157: internal call - no change needed
- `packages/sync-server/src/app-openid.ts` line 106: checks `isValidRedirectUrl(url)` - no change needed

### Pattern 3: Password Validation Return Type Change

**What:** `isValidPassword()` is currently a private type guard (`password is string`). It needs to either become a separate function that checks length, or the return type needs to carry reason codes.
**When to use:** When a boolean guard needs to become a validation with actionable error reasons.
**Example:**
```typescript
// Source: packages/sync-server/src/accounts/password.ts (current line 8)

// OPTION A: Keep isValidPassword as boolean guard, add separate validatePasswordStrength()
function isValidPassword(password: unknown): password is string {
  return password != null && password !== '';
}

function validatePasswordStrength(password: string): { error?: string } {
  if (password.length < 8) {
    return { error: 'password-too-short' };
  }
  return {};
}

// Then in bootstrapPassword and changePassword:
export function bootstrapPassword(password: string): PasswordResult {
  if (!isValidPassword(password)) {
    return { error: 'invalid-password' };
  }
  const strengthResult = validatePasswordStrength(password);
  if (strengthResult.error) {
    return strengthResult;
  }
  // ... rest unchanged
}
```

**Callers requiring no changes (login is exempt from strength check per locked decision):**
- `bootstrapPassword()` - enforce strength check
- `changePassword()` - enforce strength check
- `loginWithPassword()` - NO strength check (existing passwords must keep working)
- `checkPassword()` - NO strength check (verification only)

### Pattern 4: ReDoS Protection - Metacharacter Escape + Timeout

**What:** Two-layer defense for `regexHelper()` in handlebars-helpers.ts:
1. **Layer 1 (escape):** In the non-regex mode branch (`mapNonRegex`), escape regex metacharacters before constructing `new RegExp(value)`. This prevents payee names like `"a.+"` from being interpreted as regex.
2. **Layer 2 (timeout):** Wrap regex `.replace()` calls in a worker thread with a ~1 second timeout. Return original value if timeout fires.
**When to use:** When user-controlled strings are passed to `new RegExp()`.

```typescript
// Source: packages/loot-core/src/server/rules/handlebars-helpers.ts (current lines 51-65)

// Layer 1: escape helper (pure, no dependencies)
function escapeRegExp(str: string): string {
  return str.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
}

// Current code - mapNonRegex for 'regex' helper (line 53):
//   value => new RegExp(value)
// CHANGE TO:
//   value => new RegExp(escapeRegExp(value))

// Current code - mapNonRegex for 'replace'/'replaceAll' helpers (lines 58, 63):
//   value => value  (plain string - already safe from regex injection)
// No change needed for these - plain string .replace() is literal

// Layer 2: worker thread timeout
// The worker_threads approach for regex timeout in Node.js:
// - Create a Worker that runs the regex
// - Set a setTimeout to call worker.terminate() after ~1000ms
// - If the worker exits normally before timeout, use its result
// - If terminated, log warning and return original value

// Important: worker_threads adds meaningful complexity to a small file.
// Claude's discretion: a simpler approach is to apply escapeRegExp in non-regex
// mode (Layer 1) which addresses the sec-17 root cause (accidental ReDoS from
// payee names), plus validate that user-supplied /regex/ literals pass a
// complexity check before constructing them. Full worker thread timeout can be
// scoped to just the apply() call site.
```

**Scope clarification from code reading:**
- `regex` helper line 53: `mapNonRegex: value => new RegExp(value)` - THIS is the sec-17 vulnerability. Escape is required.
- `replace` helper line 58: `mapNonRegex: value => value` - plain string passed to `.replace()`, which is literal. No vulnerability in this branch.
- `replaceAll` helper line 63: same as `replace`. No vulnerability.
- The `/regex/flags` branch (line 52): user-authored regex literals. Escaping would break these. Timeout guard applies here.

### Anti-Patterns to Avoid

- **Don't check `iterations` in `decrypt()` to re-derive the key.** The key is already derived and loaded before `decrypt()` is called. Migration must happen at key creation time (in `createKey()`), not at decrypt time.
- **Don't add strength validation to `loginWithPassword()`.** Locked decision: existing passwords must work. Applying length check to login would lock out users with pre-existing short passwords.
- **Don't add a new env var for dev/localhost detection.** Locked decision: use `server_hostname` from config. If `server_hostname` is `http://localhost:5006`, localhost redirects are allowed. If it is a production domain, they are not.
- **Don't apply `escapeRegExp` to the regex-literal branch.** When the user writes `{{regex payee "/AMZN*/i" "Amazon"}}`, the `/AMZN*/i` is an intentional regex. Escaping it would break rule templates.
- **Don't use `pbkdf2` (async) to replace `pbkdf2Sync`.** The existing code uses the sync version. 100K iterations with SHA-512 will take roughly 100-200ms on Node 22 (acceptable for key derivation at file-open time, not a hot path). Switching to async would require propagating async through the call chain.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Regex metacharacter escaping | Custom escape regex | Standard pattern: `/[.*+?^${}()|[\]\\]/g` with `'\\$&'` | This specific pattern is the accepted standard. MDN documents it. One line. |
| PBKDF2 | Any KDF implementation | `crypto.pbkdf2Sync` (already used) | Already in codebase. Node stdlib. No external dep. |
| Worker thread boilerplate | Re-inventing MessageChannel setup | `const { Worker, isMainThread, parentPort, workerData } = require('worker_threads')` | Built-in Node.js module. Pattern is 10-15 lines. |

**Key insight:** Every fix in this phase uses Node.js stdlib or extends existing code patterns. The risk of hand-rolling comes from incorrect iteration counts, off-by-one in metacharacter escape sets, and forgetting to handle the timeout cleanup. Use verified reference patterns.

## Common Pitfalls

### Pitfall 1: PBKDF2 - Forgetting Where the Key Is Derived

**What goes wrong:** Developer adds `iterations` to `meta` in `encrypt()` but tries to use it in `decrypt()` to re-derive the key. `decrypt()` does not derive keys - it receives an already-loaded `Key` object.
**Why it happens:** The name `meta` in decrypt's signature looks like it should control decryption parameters.
**How to avoid:** Trace the call chain. `encrypt()` returns `{ value, meta }`. `decrypt()` takes a pre-loaded `Key` object from the `keys` map. The key is created by `createKey()` / `createKeyBuffer()`. The `iterations` field belongs in the stored key metadata (alongside `id`, `salt`, `base64`) not just in the encrypted-value meta.
**Warning signs:** If you can't find where `salt` is stored/read, you haven't found the right insertion point.

### Pitfall 2: PBKDF2 - Re-encryption Timing

**What goes wrong:** Re-encryption is triggered from inside `decrypt()` (encryption-internals) rather than from the higher-level file-open flow.
**Why it happens:** It seems logical to re-encrypt "right after decrypt."
**How to avoid:** Re-encryption requires calling `encrypt()` with a new key derived at 100K iterations. The encryption internals layer doesn't have access to the user's password at decrypt time. Re-encryption must happen at the `app.ts` or sync layer where both the plaintext and the ability to create a new key are available.
**Warning signs:** If the re-encrypt code needs to call `createKey()` from inside `decrypt()`, the abstraction is wrong.

### Pitfall 3: OpenID - Port Comparison on Default Ports

**What goes wrong:** `redirectUrl.port` returns `""` for `https://example.com` (default port 443) but `"443"` for `https://example.com:443`. If `server_hostname` uses one form and the client uses the other, validation fails.
**Why it happens:** `URL.port` only returns the port string when it is explicitly specified. Default ports are elided.
**How to avoid:** Use `URL.port` for comparison but test both `https://example.com` and `https://example.com:443` as `serverHostname`. In practice, `server_hostname` will be either `http://localhost:5006` or `https://mybudget.com` - explicit port on localhost, no port on production HTTPS. Since both sides come from the same source of truth, `redirectUrl.port === serverUrl.port` is safe.
**Warning signs:** Tests pass for localhost but fail for production HTTPS domain.

### Pitfall 4: Password - `isValidPassword` Return Type vs. `PasswordResult`

**What goes wrong:** Modifying `isValidPassword()` to return `{ error?: string }` instead of the type-guard `password is string` would break the TypeScript type narrowing used in callers.
**Why it happens:** It seems like the most direct approach.
**How to avoid:** Add a separate `validatePasswordStrength()` helper that is called AFTER `isValidPassword()` passes. Keep `isValidPassword()` as the type guard. This adds zero breaking changes to the four callers.
**Warning signs:** TypeScript errors on `password` type after the `if (!isValidPassword(password))` check.

### Pitfall 5: ReDoS - Worker Thread in Browser Context

**What goes wrong:** `worker_threads` is a Node.js built-in. `handlebars-helpers.ts` is in `loot-core`, which also compiles to a browser bundle (`encryption-internals.web.ts` exists in the same package).
**Why it happens:** loot-core has both Node and browser build targets.
**How to avoid:** Check whether `handlebars-helpers.ts` is used in the browser bundle. From the imports (`logger` from `../../platform/server/log`), this file imports from `platform/server/` - it is server-only. However, confirm the Vite/build config excludes it from the browser bundle before using `worker_threads`. If server-only is confirmed, `worker_threads` is safe.
**Warning signs:** Build errors when compiling the browser bundle (`@actual-app/web build`).

### Pitfall 6: PBKDF2 - pbkdf2Sync Blocks Event Loop at 100K

**What goes wrong:** 100,000 SHA-512 iterations on `pbkdf2Sync` blocks the Node.js event loop for 100-300ms per call. If this is called on a hot path (e.g., per-request), it becomes a DoS vector.
**Why it happens:** The sync variant is used (existing code decision).
**How to avoid:** This is only called at file-open time (key derivation), not on every encrypt/decrypt operation. Confirm the call path: `keyTest()` -> `createKey()` -> `pbkdf2Sync`. This happens once when a user opens their budget file. 100-300ms at file-open is acceptable. NOT acceptable on a per-transaction or per-request basis.
**Warning signs:** Performance tests showing latency on operations other than file-open.

### Worker Thread Timeout Pattern (Node.js stdlib)
```typescript
// Source: Node.js worker_threads documentation
import { Worker, isMainThread, parentPort, workerData } from 'worker_threads';

function runWithTimeout<T>(
  fn: () => T,
  timeoutMs: number,
  fallback: T,
): Promise<T> {
  return new Promise(resolve => {
    const worker = new Worker(`
      const { parentPort, workerData } = require('worker_threads');
      // execute fn logic passed via workerData
      parentPort.postMessage(result);
    `, { eval: true, workerData: { /* ... */ } });

    const timer = setTimeout(() => {
      worker.terminate();
      resolve(fallback);
    }, timeoutMs);

    worker.once('message', result => {
      clearTimeout(timer);
      resolve(result);
    });

    worker.once('error', () => {
      clearTimeout(timer);
      resolve(fallback);
    });
  });
}
```

**Note:** The `eval: true` approach passes the worker script as a string. An alternative is writing a temp file. Given MSYS constraints (from global CLAUDE.md), eval-string is simpler than file-writing for this use case, but test on Windows. The simpler alternative for this specific case is to just apply metacharacter escaping (Layer 1), which eliminates the ReDoS risk from the non-regex mode entirely without needing worker threads.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| 10,000 PBKDF2 iterations | 100,000 iterations | 2025 (this phase) | 10x harder to brute-force derived keys |
| OWASP 2017: 100K iterations | OWASP 2023: 210K iterations for SHA-512 | 2023 | Locked decision uses 100K (still 10x improvement) |
| No password length requirement | Min 8 chars (NIST 800-63B) | 2025 (this phase) | Prevents trivially guessable short passwords |
| Unconditional localhost redirect | Only when server is localhost | 2025 (this phase) | Closes open redirect in production deployments |
| Raw `new RegExp(payeeValue)` | Escaped non-regex input | 2025 (this phase) | Prevents accidental ReDoS from payee names |

**Deprecated/outdated:**
- NIST SP 800-132 (2010): recommended "at least 1000 iterations" - completely superseded. The 2023 revision process (SP 800-132 Rev 1) aligns with modern hardware threats.
- Hardcoded localhost in redirect validation: was originally a developer convenience. Should never have been in production path.
