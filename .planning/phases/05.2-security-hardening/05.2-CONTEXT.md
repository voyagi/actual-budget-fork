# Phase 05.2: Security Hardening - Context

**Gathered:** 2026-03-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Harden four security audit findings: increase PBKDF2 iterations with transparent migration, restrict OpenID redirect validation in production, add password strength requirements, and sanitize regex operations in handlebars-helpers. Addresses sec-4, sec-5, sec-7, sec-17.

</domain>

<decisions>
## Implementation Decisions

### PBKDF2 Iteration Increase (sec-4)
- Increase from 10,000 to 100,000 iterations in both `encryption-internals.ts` and `encryption-internals.web.ts`
- Migration strategy: re-encrypt on next file access (gradual, no downtime, no batch script)
- Store iteration count in encryption metadata alongside existing keyId, algorithm, iv, authTag fields
- Decrypt uses stored iteration count from metadata; encrypt always uses current default constant
- Files encrypted before this change have no iterations field in metadata, treat missing as 10,000 (backward compat)
- Re-encryption happens silently after successful decrypt, no user notification

### OpenID Redirect Restriction (sec-5)
- Remove the unconditional `localhost` allowance in `isValidRedirectUrl()` (openid.js line 444)
- Allow localhost redirects only when `server_hostname` itself is a localhost URL (auto-detects dev vs production from existing config, no new env var)
- Validate hostname, port, AND scheme must all match server_hostname (prevents open redirect and HTTP downgrade)
- Error handling: return existing `{ error: 'invalid-return-url' }` code with a server-side `console.warn` logging the blocked URL

### Password Strength Requirements (sec-7)
- Minimum 8 characters, no complexity rules (NIST 800-63B: length over complexity)
- Enforce on new passwords and password changes only, not retroactively on login
- Server-side validation in `isValidPassword()` (password.ts), no client-side JavaScript validation
- Return specific error codes (e.g. 'password-too-short') so frontend can show actionable feedback
- Existing passwords continue to work without forced change

### ReDoS Protection (sec-17)
- Protection mechanism: execution timeout (~1 second) on regex operations, no external library
- Failed or timed-out regex operations: log warning, return original value unchanged (non-disruptive)
- Escape metacharacters in regex helper's non-regex mode (`new RegExp(value)` on line 53) to prevent accidental ReDoS from payee names
- Also escape metacharacters in replace helper's plain string mode for consistency

### Claude's Discretion
- Frontend error message wording for password validation failures
- Exact timeout duration for regex execution guard
- Implementation details for transparent re-encryption trigger (where in the decrypt/open flow to re-encrypt)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `encryption-internals.ts` (Node/server): `createKeyBuffer()` uses `crypto.pbkdf2Sync()` with 10000 iterations at line 81
- `encryption-internals.web.ts` (browser): `createKey()` uses `crypto.subtle.deriveKey()` with PBKDF2/10000 at line 80
- Encryption metadata already stores `keyId`, `algorithm`, `iv`, `authTag` - adding `iterations` extends the existing pattern
- `isValidRedirectUrl()` in openid.js line 431 - the function to modify for redirect restriction
- `isValidPassword()` in password.ts line 8 - the validation entry point used by bootstrap, login, change, check
- `regexHelper()` in handlebars-helpers.ts line 23 - the wrapper creating RegExp from user input

### Established Patterns
- Encryption metadata is passed as a plain object alongside encrypted values (encrypt/decrypt functions)
- Error codes are string constants returned in `{ error: 'code' }` objects
- Config values read via `config.get()` from convict-based load-config.ts
- Rate limiting already in place on auth endpoints (Phase 04.1)

### Integration Points
- PBKDF2: Both encryption-internals files must stay in sync (same iteration count, same metadata format)
- PBKDF2: Callers of createKey/createKeyBuffer need no changes if metadata is extended transparently
- OpenID: Only `isValidRedirectUrl()` needs modification; callers already check its boolean return
- Password: `isValidPassword()` return type needs to change from boolean to include error reason, or add separate validation function
- ReDoS: `regexHelper()` is internal to handlebars-helpers.ts, changes are self-contained

</code_context>
