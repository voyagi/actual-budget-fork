### Pattern 1: Express Auth Rate Limiter (sec-2)

**What:** A separate `rateLimit()` instance applied only to auth endpoints as route-level middleware.
**When to use:** Auth endpoints that need stricter limits than the global 500/min.
**Example:**

```typescript
// Source: verified against express-rate-limit usage in app.ts and app-cors-proxy.ts
const authRateLimit = rateLimit({
  windowMs: 15 * 60 * 1000, // 15 minutes
  max: 5,
  legacyHeaders: false,
  standardHeaders: true,
  message: { status: 'error', reason: 'too-many-requests' },
});

// Applied as route-level middleware in app.ts:
// app.use('/account/login', authRateLimit);
// app.use('/account/bootstrap', authRateLimit);
// app.use('/openid', authRateLimit);
```

The auth routes are on sub-apps (`/account` routes live in app-account.ts, `/openid` in app-openid.ts). Rate limiting can be applied in `app.ts` before the sub-app is mounted using `app.use('/account/login', authRateLimit, accountApp.handlers)` - but sub-app mounting doesn't support path narrowing this way. The correct approach is to apply at the top-level before sub-app delegation:

```typescript
// In app.ts, before app.use('/account', accountApp.handlers):
app.use(['/account/login', '/account/bootstrap', '/openid'], authRateLimit);
app.use('/account', accountApp.handlers);
app.use('/openid', openidApp.handlers);
```

### Pattern 2: CORS with Origin Whitelist (cfg-2)

**What:** Pass origin option to `cors()` from convict config field.
**When to use:** Any production server that should only accept requests from its own frontend.


### Pattern 3: Security Headers Middleware (sec-1, sec-6)

**What:** Inline middleware function setting HSTS and CSP headers before routes.
**When to use:** After CORS, before route handlers.
**Example:**

```typescript
// In app.ts, after cors(), before rate limiting:
if (process.env.NODE_ENV !== 'development') {
  app.use((_req, res, next) => {
    // HSTS - tell browsers to use HTTPS for 1 year
    res.set('Strict-Transport-Security', 'max-age=31536000');
    // CSP - restrict resource origins
    res.set(
      'Content-Security-Policy',
      [
        "default-src 'self'",
        "script-src 'self'",
        "style-src 'self' 'unsafe-inline'",   // React inline styles require this
        "img-src 'self' data:",                // data: for inline icons
        "font-src 'self'",
        "connect-src 'self'",
        "frame-ancestors 'none'",
      ].join('; '),
    );
    next();
  });
}
```

Note: HSTS is sent conditionally because sending HSTS over HTTP (development) causes browsers to refuse future HTTP connections, breaking local dev.

### Pattern 8: localStorage Key Cleanup (dsg-5)

**What:** On mount, scan localStorage for old consent-dismissed-* keys and delete them.
**When to use:** Any feature that writes daily keys to localStorage.
**Example:**

```typescript
// In ConsentExpiryBanner.tsx - add useEffect on mount:
React.useEffect(() => {
  const today = new Date().toDateString();
  const keysToDelete: string[] = [];
  for (let i = 0; i < localStorage.length; i++) {
    const key = localStorage.key(i);
    if (key?.startsWith('consent-dismissed-') && !key.endsWith(today)) {
      keysToDelete.push(key);
    }
  }
  for (const key of keysToDelete) {
    localStorage.removeItem(key);
  }
}, []); // Empty deps: runs once on mount
```

The two-pass approach (collect then delete) avoids index invalidation while iterating `localStorage`.

### Anti-Patterns to Avoid

- **HSTS in development:** Never send Strict-Transport-Security over HTTP. Gate it on `NODE_ENV !== 'development'`.
- **CSP frame-src vs frame-ancestors:** `frame-ancestors` replaces X-Frame-Options. Use `frame-ancestors 'none'` in CSP, not a separate header.
- **aria-live on every element:** Only add to the outermost container of a status component, not nested children. Multiple nested `aria-live` regions cause double-announcements.
- **Deleting localStorage keys during iteration:** Iterating by index while deleting corrupts the index. Always collect keys first, then delete.
- **Inline styles on focus-visible pseudoclass:** React inline styles cannot express pseudoclasses. Must use `@emotion/css` css() function (already used in FinancesApp.tsx for skip-nav).

## Common Pitfalls

### Pitfall 1: a11y-2 Skip Navigation May Already Be Implemented

**What goes wrong:** Planner creates a task to add skip-nav that overwrites the existing implementation.
**Why it happens:** The audit identified "no skip-navigation link" but FinancesApp.tsx already has one at lines 327-351.
**How to avoid:** Planner should check if a11y-2 is "verify existing skip-nav works correctly" rather than "add skip-nav". The link exists with correct `href="#main-content"`, and `id="main-content"` exists in Page.tsx. Task should focus on verifying it works (tab focus appears) and has the correct text.
**Warning signs:** If the task says "add a skip-nav link" without acknowledging the existing implementation.

### Pitfall 2: CORS Origin Must Be a String (Not Array) in the Convict Field

**What goes wrong:** Setting `corsOrigin` as an Array format in convict to support multiple origins, but the cors package expects different syntax for arrays.
**Why it happens:** Multi-origin support is a common goal but the user decision is a single String env var.
**How to avoid:** Keep as String format. The cors package `origin` option accepts a string directly. If multi-origin is needed later, it's a separate decision.

### Pitfall 3: Auth Rate Limiter Must Be Mounted Before Sub-App in app.ts

**What goes wrong:** Adding rate limiting inside `app-account.ts` affects all /account routes (including non-auth routes like `/account/validate`, `/account/change-password`).
**Why it happens:** It's tempting to add rate limiting inside the sub-app file.
**How to avoid:** Add the `authRateLimit` middleware in `app.ts` using path-specific mounting: `app.use(['/account/login', '/account/bootstrap'], authRateLimit)` before `app.use('/account', accountApp.handlers)`.

### Pitfall 4: res.json() vs res.send() for Content-Type Fix (sec-16)

**What goes wrong:** Adding `res.set('Content-Type', 'application/json')` before `res.send(fileAccessError)` when `res.json(fileAccessError)` would be cleaner.
**Why it happens:** The FIXME suggests fixing Content-Type but the simpler fix is switching to `res.json()`.
**How to avoid:** Replace `res.send(fileAccessError)` with `res.json(fileAccessError)`. The express `json()` method automatically sets Content-Type: application/json.

### Pitfall 5: Terser Removal May Expose Build Configuration

**What goes wrong:** Removing `compress: false, mangle: false` enables terser, but sourcemaps are still enabled (`sourcemap: true` line 119). This is intentional (sourcemaps are separate files, not embedded).
**Why it happens:** Concern that sourcemaps expose source structure.
**How to avoid:** Leave sourcemap: true as-is. Sourcemaps are separate .map files, not embedded in the bundle. They don't expose source to end users unless explicitly fetched. This is a separate decision from compression.

### Pitfall 6: Iterating localStorage by Index While Deleting

**What goes wrong:** Standard `for (let i = 0; i < localStorage.length; i++)` loop that calls `localStorage.removeItem()` during the loop corrupts the index, causing some keys to be skipped.
**Why it happens:** localStorage.length decrements when an item is removed.
**How to avoid:** Two-pass: collect matching keys into an array first, then delete all in a second loop.

   - What's unclear: Whether any client-side code makes direct calls to `api.enablebanking.com`.

3. **boolToInt FIXME in app-sync.ts - Safe to convert?**
   - What we know: Line 454 converts `file.deleted` to 0/1 with a FIXME to make it boolean. The frontend receives this value.
   - What's unclear: Whether the frontend (loot-core) currently treats this value as an integer or boolean. Changing to boolean could break the frontend.
   - Recommendation: Leave the boolToInt conversion FIXME as-is (keep integer) unless there's explicit frontend evidence it handles boolean. The FIXME describes the aspirational state, not a safe same-day fix. Focus on the 404 status code fix instead, which is clearly safe.
