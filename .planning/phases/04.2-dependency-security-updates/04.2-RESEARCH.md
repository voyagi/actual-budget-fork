## Summary

The yarn.lock currently contains multiple vulnerable package versions that Trivy has flagged across 10 CVEs (affecting 7 distinct packages). Research reveals the landscape is partially better than it appears: the remote master branch already has Dependabot commits (PR#5 and PR#6, merged Feb 27-28) that updated tar from 7.5.1 to 7.5.9 and storybook from 10.2.0 to 10.2.10. The working branch (`chore/state-update`) needs to incorporate those changes.

The rollup resolution pin (4.40.1) was added to deduplicate vite versions (upstream PR#4943: "removes 4 MB, ensures only one version of vite needs security monitoring"). The pin is a Yarn `resolutions` workaround to force a single rollup version across all vite sub-dependencies. Bumping it to 4.59.0 is safe because: (1) rollup 4.40.1 to 4.59.0 has no breaking changes - it is a series of minor/patch releases; (2) vite 7.3.1 (the project's current vite version) requires `"rollup": "^4.43.0"` as a direct dependency, so 4.40.1 is already technically below vite 7's own lockstep requirement; (3) the CVE fix (path traversal in output filename sanitization) is a behavioral guard with no API changes.

Three CVEs (jws 3.x, serialize-javascript, glob, ajv) affect transitive dependencies only and require resolution overrides rather than direct version bumps. The lockfile refresh strategy correctly handles direct dep CVEs (axios, lodash) since their package.json ranges already declare the safe versions.

**Primary recommendation:** Rebase/merge the current branch onto remote master first (to inherit the Dependabot tar and storybook updates), then run `yarn install` to refresh the lockfile, then apply surgical resolution overrides for the remaining transitive CVEs (jws 3.x, serialize-javascript, glob, ajv), and finally bump the rollup pin from 4.40.1 to 4.59.0.

### Rollup Pin Deep Dive (sec-9)

**Why it was pinned:** The upstream comment (removed in a later commit) stated: `"//rollup": "Pinned to deduplicate vite's nested rollup versions (see PR #2369, #4943)"`. PR#4943 ran `yarn dedupe` to consolidate two versions of vite to one, with rollup pinned as a side-effect to prevent version fragmentation. The pin is a deduplication convenience, not a compatibility requirement.

**Why 4.40.1 -> 4.59.0 is safe:**
- Vite 7.3.1 (current) ships rollup as a direct dep at `"^4.43.0"` - meaning the 4.40.1 pin is already below what vite 7 uses internally. Yarn resolves this by satisfying both: the `resolutions` forces all workspace packages to 4.40.1 even though vite's own code imports a newer version within its bundled node_modules.
- Rollup 4.40.1 to 4.59.0 releases: no breaking changes. All minor version bumps add features (tree-shaking improvements, namespace handling, import attributes). One deprecation warning in 4.57.0 about returning import attributes from load/transform hooks (Rollup 5 change, not 4.x).
- The CVE fix itself (path traversal guard, "Throw when generated bundle contains paths leaving the output directory") is a pure safety check - no build behavior changes for normal inputs.

**Recommended update:** Change `"rollup": "4.40.1"` to `"rollup": ">=4.59.0"` (range, not exact pin) in `resolutions`. Using a range is better than an exact pin because it allows Dependabot to bump it automatically in future, while still enforcing deduplication. Alternatively, exact pin `"4.59.0"` is fine if the deduplication goal is the primary concern.

## Architecture Patterns

### Pattern 1: Yarn Resolutions for Transitive CVE Override

**What:** Adding an entry to the root `package.json` `resolutions` field forces a specific version for a transitive dependency regardless of what parent packages declare.

**When to use:** When a vulnerable package is a transitive dep that cannot be upgraded by bumping a direct dep within semver range.

**Example:**
```json
// Root package.json resolutions section
"resolutions": {
  "@codemirror/view": ">=6.39.15",
  "@isaacs/brace-expansion": ">=5.0.1",
  "qs": ">=6.14.1",
  "rollup": ">=4.59.0",
  "socks": ">=2.8.3",
  "jws": ">=3.2.3",
  "serialize-javascript": ">=7.0.3",
  "glob": ">=10.5.0",
  "ajv": ">=8.18.0"
}
```

**Confidence:** HIGH - this is the documented Yarn Berry mechanism for CVE remediation of transitive deps.

### Pattern 2: Lockfile Refresh for Direct Dep CVEs

**What:** When a direct dep's package.json range already declares the safe version (`"^1.13.5"` for axios), running `yarn install` causes Yarn to re-evaluate ranges and pull in the latest satisfying version.

**When to use:** CVEs where package.json already has the safe range declared but the lockfile still resolves an older version (common after upstream commits that bump ranges but lockfile wasn't committed).

**Example:**
```bash
# After verifying package.json has the right range:
# sync-server/package.json: "axios": "^1.13.5"
# desktop-client/package.json: "lodash": "^4.17.23"
yarn install
# Verify in yarn.lock:
# "axios@npm:^1.13.5": version: 1.13.5  (old 1.12.2 entry removed)
# "lodash@npm:^4.17.23": version: 4.17.23 (old 4.17.21 entry removed)
```

### Pattern 3: Range vs Exact Pin in Resolutions

**What:** Yarn resolutions accept both exact versions (`"4.59.0"`) and ranges (`">=4.59.0"`).

**Prefer ranges** for CVE remediations because:
- Exact pins freeze the dependency and prevent Dependabot from automatically bumping to newer security patches
- Ranges continue to auto-update within the constraint
- The `>=X.Y.Z` form says "anything at or above the fixed version"

**Prefer exact pins** only when:
- Deduplication is the goal (multiple semver-incompatible versions would otherwise exist)
- A specific version has a confirmed regression in later versions

### Anti-Patterns to Avoid

- **Exact-pinning all resolution overrides:** Freezes security fixes, prevents Dependabot automation. Use `>=X.Y.Z` ranges.
- **Bumping minimatch 3.x to 10.x via resolutions:** Major version mismatch. `brace-expansion` v1 API (used by minimatch 3.x) is incompatible with minimatch 10.x. Force-resolving to 10.x will break consumers expecting 3.x API.
- **Running `yarn upgrade` (Berry):** Berry no longer has `yarn upgrade` - it was replaced by `yarn up`. Using `yarn upgrade` will fail or upgrade interactively.
- **Ignoring the storybook WebSocket CVE:** While dev-only, it enables RCE on developer machines. The fix is free (within declared range) once remote master is merged.
- **Skipping `yarn dedupe` after bulk changes:** Can leave redundant lockfile entries that confuse future dependency audits.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| CVE verification | Manual version checks | `trivy fs .` | Trivy catches transitive deps, resolutions overrides, and yarn.lock vs node_modules discrepancies |
| Lockfile refresh | Delete and re-generate yarn.lock | `yarn install` | Full delete breaks PnP caching and may change unrelated resolutions |
| Resolution override | Modifying yarn.lock directly | package.json `resolutions` + `yarn install` | Direct lockfile edits are overwritten by next install |
| Version range validation | Read package.json manually | `yarn info <pkg> versions` | Shows all available versions in npm registry |

**Key insight:** Never edit yarn.lock directly. All intentional changes go through package.json (direct deps or resolutions) + `yarn install`. Yarn Berry validates lockfile integrity against package.json on every install.

## Common Pitfalls

### Pitfall 1: Branch Divergence from Remote Master

**What goes wrong:** The working branch (`chore/state-update`) diverges from remote master which has Dependabot commits (65f489be0) that already updated tar and storybook in the lockfile. Doing the lockfile refresh without first syncing will re-resolve tar to 7.5.1 (vulnerable) and storybook to 10.2.0 (vulnerable) because the local package.json still has the old ranges.

**Why it happens:** Dependabot PR was merged into remote master but the current working branch was not updated.

**How to avoid:** Rebase or merge from `origin/master` before starting the lockfile refresh. Confirm `git log --oneline origin/master -5` shows the Dependabot commit before proceeding.

**Warning signs:** yarn.lock shows storybook 10.2.0 after `yarn install` (should be 10.2.x >= 10.2.10).

### Pitfall 2: Rollup Resolution Pin Breaking Vite

**What goes wrong:** Updating `"rollup": "4.40.1"` to `"rollup": ">=4.59.0"` causes Yarn to resolve rollup to the very latest version (e.g., 4.x.y future release) which might introduce unexpected behavior.

**Why it happens:** `>=` with no upper bound always picks the latest. Rollup 5.x is in development and would be a breaking change.

**How to avoid:** Use `"rollup": ">=4.59.0 <5.0.0"` to stay within the 4.x major line, or use exact `"4.59.0"` for maximum safety.

**Warning signs:** Build failure with messages about API changes in rollup plugins (`@rollup/plugin-inject`, `rollup-plugin-visualizer`).

### Pitfall 3: Minimatch Resolution Override Breaking Tools

**What goes wrong:** Adding `"minimatch": ">=10.2.3"` to resolutions forces ancient tools (electron-rebuild, node-gyp, older webpack configs) to use minimatch 10.x which has a different brace-expansion dependency. These tools import `minimatch` and call it with assumptions about v3 API.

**Why it happens:** Minimatch 3.x, 5.x, 9.x, 10.x all exist in the lockfile because different packages require different major versions. A broad resolution override breaks the ones that only work with specific majors.

**How to avoid:** Use the namespace pattern: `"**minimatch@^3.0.0": ">=3.1.3"` to only fix the 3.x range, leaving 5.x, 9.x, 10.x alone. Or accept 3.x minimatch CVEs as unfixable transitive risk in build tools (the attack requires attacker-controlled regex patterns in build toolchain - limited practical risk).

**Warning signs:** `yarn install` completes but `yarn build` fails with "Cannot read properties of undefined" in brace-expansion or node-gyp tools.

### Pitfall 4: Axios 1.12.2 Persisting After Lockfile Refresh

**What goes wrong:** After `yarn install`, the old `"axios@npm:^1.2.1": version: 1.12.2` entry might remain if `nordigen-node` or another package still declares `"axios": "^1.2.1"` in its own package.json (semver-compatible with 1.12.x).

**Why it happens:** The `^1.2.1` range is satisfied by both 1.12.2 and 1.13.5. Yarn keeps the existing lockfile entry if the version satisfies all constraints.

**How to avoid:** Check if axios 1.12.2 persists after refresh. If it does, add `"axios": ">=1.13.5"` to resolutions to force the safe version.

**Warning signs:** `grep "axios" yarn.lock` shows both `1.12.2` and `1.13.5` entries after refresh.

### Pitfall 5: Serialize-javascript Resolution Not Applying

**What goes wrong:** Adding `"serialize-javascript": ">=7.0.3"` to resolutions doesn't update the lockfile entry.

**Why it happens:** serialize-javascript 6.0.2 is required by webpack-related packages that declare `"serialize-javascript": "^6.0.0"`. Yarn resolutions for security overrides work with `>=` but only if the registry has 7.0.3 tagged under the same dist-tag. The jump from major 6 to 7 may not be covered by Yarn's resolution inference.

**How to avoid:** After adding the resolution and running `yarn install`, verify with `grep "serialize-javascript" yarn.lock`. If 6.0.2 persists, use the exact namespaced form: `"serialize-javascript": "7.0.3"` (exact, not range) which forces Yarn to use it regardless of semver incompatibility.

**Warning signs:** `yarn.lock` still shows `version: 6.0.2` after install.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `yarn audit fix` (npm compat) | `resolutions` in package.json + `yarn install` | Yarn 2+ (Berry) | No equivalent of `yarn audit fix` in Berry; resolutions is the prescribed mechanism |
| Exact pins in resolutions | Range overrides (`>=X.Y.Z`) | Best practice evolution 2024+ | Ranges allow Dependabot to auto-bump; exact pins freeze forever |
| Ignoring transitive CVEs | Resolution overrides for all transitive CVEs | Security compliance requirements 2025 | Trivy and GitHub Dependabot now flag transitive CVEs as blocking |

**Deprecated/outdated:**
- `yarn upgrade`: Removed in Berry (Yarn 2+). Use `yarn up` instead.
- `yarn audit`: Available in Berry but doesn't have `--fix`. Use resolutions manually.
- Editing yarn.lock directly: Overwritten on next install. Never do this.
