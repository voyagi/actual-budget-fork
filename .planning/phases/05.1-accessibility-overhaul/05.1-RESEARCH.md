## Summary

This phase addresses three audit findings that can each be implemented as an independent task with no cross-cutting risk. The work is isolated to fork-added files only - the constraint against touching upstream code is absolute to prevent merge conflicts.

The phase has a clear implementation order: dx-3 (utility extraction) should come first because a11y-3 and a11y-6 are pure additive changes that don't touch any shared infrastructure. The urgency utility extraction (dx-3) is the most structural change - it moves existing logic, not adds new logic - and should be validated before the ARIA work builds on the same components.

The key insight from reading the source is that the `FormError` component already accepts `id` and `role` as props, and `SingleInputModal.tsx` already demonstrates the correct pattern: `id="single-input-error"`, `role="alert"`, and `aria-describedby="single-input-error"` on the input. The planner must replicate this exact pattern for fork forms. The only open question in the `Claude's Discretion` section - whether `role="alert"` should be a default prop - is answered clearly: make it a default, as all error display uses it as an alert.

**Primary recommendation:** Implement in this order: (1) dx-3 urgency utility, (2) a11y-3 heading hierarchy, (3) a11y-6 form ARIA. Each is a single-file or minimal-file change with zero cross-component side effects.

### Pattern 1: Semantic Heading Hierarchy

**What:** Replace styled `<Text>` section titles with `<h2>` or `<h3>` elements that carry visual styling inline.
**When to use:** Any section title that is not inside a modal header (which renders `<h2>` via ModalHeader) and identifies a distinct content region.

**Critical context:** `PageHeader` and `MobilePageHeader` render `<h1>`. `ModalHeader` renders the modal's title as `<h2>` via its internal implementation (confirmed: ModalHeader wraps title in an accessible heading). Fork pages that render inside `<Page>` inherit `<h1>` from the page title. Fork pages that render as modals inherit `<h2>` from ModalHeader.

**Consequence for fork pages:**
- `BankSync` (index.tsx) renders inside `<Page header="Bank Sync">` which produces `<h1>`. Its sync provider group titles (`GoCardless`, `Enable Banking`, etc.) should be `<h2>`.
- `EditSyncAccount` is a modal (ModalHeader = `<h2>` title). Section titles "Field mapping" and "Options" should be `<h3>`.
- `MobileBankSyncAccountEditPage` renders inside `<Page>` with `<MobilePageHeader>` (= `<h1>`). Section titles "Field mapping" and "Options" should be `<h2>`.
- `MobileBankSyncPage` renders inside `<Page>` (= `<h1>`). No distinct section titles requiring headings.
- `EnableBankingExternalMsgModal` is a modal (ModalHeader = `<h2>`). No sub-sections requiring additional headings.
- `SelectLinkedAccountsModal` is a modal (ModalHeader = `<h2>`). The table header row is not a heading - no additional semantic headings needed.
- `ConsentExpiryBanner` is a status strip, not a page - no headings needed.

**Verified pattern from existing codebase:**
```tsx
// Source: packages/desktop-client/src/components/banksync/EditSyncAccount.tsx lines 207-210
// Current code (styled Text, no semantic heading):
<Text style={{ fontSize: 15 }}>
  <Trans>Field mapping</Trans>
</Text>

// After change (h3 because EditSyncAccount is a modal, ModalHeader already renders h2):
<h3 style={{ fontSize: 15, margin: 0, fontWeight: 'inherit' }}>
  <Trans>Field mapping</Trans>
</h3>
```

**Inline style reset required:** `<h3>` elements have browser default `margin` and `font-weight: bold`. Reset with `style={{ margin: 0, fontWeight: 'inherit' }}` (or match the existing Text style) to maintain visual identity while adding semantics.

```typescript
// packages/desktop-client/src/utils/consent-urgency.ts

import {
  SvgExclamationOutline,
  SvgExclamationSolid,
  SvgInformationOutline,
} from '@actual-app/components/icons/v1';
import { theme } from '@actual-app/components/theme';

import type { ConsentUrgency } from '@desktop-client/hooks/useEnableBankingStatus';

export { type ConsentUrgency };  // re-export for consumers

export function getUrgencyLevel(daysUntilExpiry: number): ConsentUrgency {
  if (daysUntilExpiry <= 0) return 'expired';
  if (daysUntilExpiry <= 7) return 'urgent';
  if (daysUntilExpiry <= 14) return 'soon';
  return 'ok';
}

export const urgencyColors: Record<
  ConsentUrgency,
  { text: string; background: string; border: string }
> = {
  expired: {
    text: theme.errorText,
    background: theme.errorBackground,
    border: theme.errorText,
  },
  urgent: {
    text: theme.warningText,
    background: theme.warningBackground,
    border: theme.warningText,
  },
  soon: {
    text: theme.noticeText,
    background: theme.noticeBackground,
    border: theme.noticeText,
  },
  ok: {
    text: theme.pageText,
    background: theme.pageBackground,
    border: theme.pageTextSubdued,
  },
};

export const urgencyIcons = {
  expired: SvgExclamationSolid,
  urgent: SvgExclamationOutline,
  soon: SvgInformationOutline,
  ok: null,
} as const;
```

### Anti-Patterns to Avoid

- **Adding `aria-hidden` to decorative icons in urgency banner:** The urgency icons in ConsentExpiryBanner are decorative (the message text repeats the urgency semantically). They should have `aria-hidden="true"`. The Phase 04.1 summary mentions `BankSyncStatus spinning icon lacks aria-hidden` - same principle applies to urgency banner icons (they're in the existing banner, not a new change, but worth confirming during task execution).
- **Using `<div>` or styled `<View>` instead of semantic heading:** The whole point of a11y-3. Always use `<h2>`/`<h3>` native elements.
- **Setting `aria-describedby` unconditionally:** Point to the error id only when the error is visible. Pass `aria-describedby={hasError ? 'error-id' : undefined}` - this is the pattern shown in SingleInputModal.
- **Mutating FormError's `role` in callers after the default change:** The default `role="alert"` is correct for all error display. No callers should override it to `undefined` or any other value.
- **Circular import between consent-urgency.ts and useEnableBankingStatus.ts:** The `ConsentUrgency` type must be defined in `consent-urgency.ts` first. The hook then imports from the utility. The utility imports from `@actual-app/components` only - no circular dependency.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Accessible error announcement | Custom event system or focus management | `role="alert"` on FormError | Browser and AT handle announcement automatically when role is present |
| Heading identification for screen readers | Custom `aria-role="heading"` or `aria-level` on div | Native `<h2>`, `<h3>` elements | Native elements have full AT support; aria-role requires correct aria-level too |
| Form label association | Proximity heuristics | `htmlFor` + `id` pairing or `aria-label` | Only explicit association is reliable across all screen readers |

**Key insight:** All three audit findings are "use what browsers already know" problems. Semantic HTML elements (`<h2>`, `<h3>`) and standard ARIA attributes (`role="alert"`, `aria-describedby`) are universally supported. There is no case where a custom implementation outperforms native browser semantics.

## Common Pitfalls

### Pitfall 1: Heading Level Mismatch in Modal Context
**What goes wrong:** Adding `<h2>` to a section inside a modal whose title is already an `<h2>`, creating a flat/broken outline (h1 > h2 > h2 instead of h1 > h2 > h3).
**Why it happens:** ModalHeader renders its title as a heading (commonly h2 in upstream implementation). Adding h2 section titles inside the modal creates duplicate h2s at the same level.
**How to avoid:** Sections within modals get `<h3>`. Sections on full pages (where h1 is the page title) get `<h2>`. Verify ModalHeader heading level before assigning section level.
**Warning signs:** Screen reader navigation shows multiple h2s inside a single modal.

### Pitfall 2: aria-describedby Pointing to Hidden Element
**What goes wrong:** `aria-describedby="error-id"` set unconditionally when the FormError is conditionally rendered (e.g., only shown when `errorMessage !== null`).
**Why it happens:** Developer sets the attribute statically and conditionally renders the target.
**How to avoid:** Use `aria-describedby={errorMessage ? 'error-id' : undefined}` as shown in SingleInputModal. When `undefined`, React removes the attribute from the DOM.
**Warning signs:** Screen reader announces "error-id" element that doesn't exist or announces stale error text after the error is cleared.

### Pitfall 3: FormError Default Role Breaks Storybook Stories
**What goes wrong:** Adding `role="alert"` as default causes Storybook story for FormError to render with an alert role, potentially triggering AT announcements during development.
**Why it happens:** Storybook renders components in isolation.
**How to avoid:** This is acceptable behavior - FormError IS an alert role component. No mitigation needed. The Storybook story (FormError.stories.tsx) does not need updating.

### Pitfall 4: oxfmt Formatting on Modified Files
**What goes wrong:** Modified files fail the `oxfmt --check` lint gate in CI.
**Why it happens:** Inline style objects and JSX formatting must match oxfmt's output.
**How to avoid:** Run `npx oxfmt <modified-file>` after every edit. The CLAUDE.md documents the fork-scoped command.
**Warning signs:** CI lint step fails after commit.

### Pitfall 5: Import Path for New Utility File
**What goes wrong:** Using a relative import (`../../utils/consent-urgency`) instead of the workspace alias (`@desktop-client/utils/consent-urgency`).
**Why it happens:** Reflex to use relative paths.
**How to avoid:** All other imports in fork files use `@desktop-client/` prefix. Check `tsconfig.json` alias definition. The correct import is `@desktop-client/utils/consent-urgency`.
