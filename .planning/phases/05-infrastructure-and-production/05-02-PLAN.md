Add a production trust module backed by account.sqlite.

Implementation requirements:
1. Create a `production_trust_state` table idempotently from the new trust utility. Use stable condition keys: `access`, `persistence`, `multi_device_sync`, and `bank_sync`.
2. Persist at least: condition key, status (`trusted` or `untrusted`), reason code, user-facing message key or summary, last checked timestamp, last verified timestamp, recovery source (`automated` or `manual`), and non-secret evidence details.
3. Expose authenticated routes in a dedicated app, mounted from `app.ts` before static frontend routes:
   - `GET /production-trust` returns current aggregate state and rows.
   - `POST /production-trust/record` records an untrusted condition from automated checks or verification flows.
   - `POST /production-trust/check` runs supported automated recovery checks and only marks affected rows trusted when the check passes.
   - `POST /production-trust/manual-verify` records an explicit verified manual fix for conditions that cannot be proven server-side, such as phone HTTPS trust.
4. Reuse `validateSessionMiddleware`; do not make trust-state mutation endpoints public.
5. Do not reuse `/alerts/acknowledge` as a clearing path. Operational alerts may still exist, but production trust state is independent and durable.
6. Implement the bank-sync automated recovery check from `eb_sync_log`: a recent `ok` row for a linked Actual account can clear `bank_sync`; a recent error or missing recent status records `bank_sync` as untrusted.
7. Keep access, persistence, and multi-device checks capable of manual verification. Add automated checks only where the server can prove the condition without false confidence.
8. Return one aggregate response shaped for UI consumption: `isTrusted`, `activeConditions`, `lastCheckedAt`, and `canRunAutomatedCheck`.

<threat_model>
Threats:
- False positive trust: warning clears without the production condition being verified.
- False negative warning: stale access, persistence, multi-device sync, or bank sync failures remain hidden.
- Unauthorized mutation: unauthenticated callers mark production trust state as healthy.
- Secret leakage: trust evidence stores tokens, bank identifiers, OAuth data, or raw error payloads.
- Alert confusion: dismissing operational alerts accidentally clears production trust state.
- UI blocking: production warning prevents normal budget viewing or transaction entry.

Mitigations:
- Store trust state durably in account.sqlite and clear only through explicit automated check success or verified manual fix.
- Put all trust mutation routes behind `validateSessionMiddleware`.
- Store reason codes and sanitized evidence only; never store secrets or raw bank credentials.
- Keep production trust state independent from `/alerts/acknowledge`.
- Mount a non-blocking app-shell warning and test that normal workflows remain usable.
- Add tests for stale/missing/error bank-sync rows and for acknowledgement not clearing trust.
</threat_model>
